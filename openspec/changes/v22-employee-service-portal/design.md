## Context

v2.2 将系统绑定到企业内部服务台工单场景，员工服务端负责工单业务的发起、补充、跟踪和验收。当前前端已经有登录、工单列表和详情基础能力，但页面表达仍偏“普通用户提交文本”，缺少员工档案、服务类型、关键信息填写、员工视角清洗、验收反馈和申诉升级的统一闭环。

## Goals / Non-Goals

**Goals:**

- 将员工服务端实现为内部员工的服务请求门户。
- 支持服务类型选择、问题描述、关键信息填写、补充沟通、进度跟踪、结果验收和申诉升级。
- 保证员工只能看到自己的工单和用户可理解的处理结果。
- 与智能处理引擎、服务台处理端的 `waiting_user_input` 和 feedback 流程打通。

**Non-Goals:**

- 不实现完整客服 IM、多人协同编辑、附件对象存储和短信邮件通知。
- 不实现企业级组织架构、细粒度 RBAC、SSO。
- 不向员工暴露知识库相似度、Agent 置信度、Prompt、Trace 原始调试字段。

## Decisions

1. **员工侧以工单详情页作为协同中心。**  
   入口页负责创建和筛选，详情页负责状态进度、补充材料、结果查看、验收和申诉，避免把业务动作散落在多个页面。

2. **工单内容采用“员工可见内容 + 内部结构化字段”双视角。**  
   后端保留分类、优先级、风险和 Agent 判断，员工接口返回时清洗为原始描述、进度、处理建议和补充提示；服务台和运维接口保留内部字段。

3. **补充材料复用 `ticket_messages`。**  
   员工补充、审核员请求补充都落到同一消息表，通过 `sender_type` 和 metadata 区分来源，工作流恢复时读取最近上下文。

4. **结果验收和申诉走反馈接口。**  
   `satisfied` 仅记录满意度；`dissatisfied` 自动触发 `user_request` 人工审核，让服务台接管。

## Risks / Trade-offs

- **材料采集过细导致提单门槛变高** -> 关键信息字段默认可选，仅在预诊断或服务台请求补充时强调必填。
- **员工看不到内部依据会觉得系统不透明** -> 展示“处理依据摘要”和“处理进度”，但不展示相似度、置信度、Prompt 等调试字段。
- **验收反馈重复提交造成状态混乱** -> 每个 completed 工单只允许一次正式验收反馈，重复提交返回 409。
