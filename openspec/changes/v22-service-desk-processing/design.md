## Context

服务台处理端承接企业内部服务台的人工业务职责：处理智能引擎无法自动闭环的工单、核查 AI 建议、要求员工补充材料、维护处理知识并分析运营情况。旧文档把这些能力散落在管理员模块、知识库和审核工作台中，v2.2 需要统一为服务台处理端。

## Goals / Non-Goals

**Goals:**

- 提供待办工单受理与筛选能力。
- 提供人工审核工作台，支持通过、改写、重处理、驳回、请求补充五类决策。
- 提供知识维护能力，覆盖上传、入库审核发布、更新和回滚。
- 提供运营分析，展示处理状态、审核质量、员工反馈和 AI 建议采纳情况。

**Non-Goals:**

- 不实现客服坐席 IM、排班、认领锁定、多人会签和 SLA 计时。
- 不实现真实退款、行政流程审批或外部业务系统写操作。
- 不承担系统账号治理、Prompt/RAG 调试和系统健康监控，这些归属系统运维管理端。

## Decisions

1. **服务台处理端以工单待办队列驱动。**  
   待审队列和待办列表按状态、分类、优先级、触发原因筛选，点击后进入统一详情核查与决策面板。

2. **人工审核决策保持有限枚举。**  
   继续使用 `approve`、`rewrite`、`reprocess`、`reject`、`request_info`，所有决策写入 `human_reviews`，并通过状态机恢复或暂停。

3. **知识维护强调业务发布状态。**  
   上传文档后不只写入知识库，还要展示解析、入库、发布或失败状态；版本回滚保留历史记录。

4. **运营分析使用已有业务数据聚合。**  
   处理状态来自 tickets，审核质量来自 human_reviews，员工反馈来自 feedback，AI 建议采纳率比较推荐决策和最终决策。

## Risks / Trade-offs

- **审核入口过多导致职责混乱** -> 统一用服务台处理端承接人工审核和知识维护，账号/策略/健康移出到系统运维管理端。
- **知识发布失败影响处理质量** -> 失败状态必须可见，保留待发布记录，允许重试或回滚。
- **运营指标可能因 demo 数据少而波动大** -> 页面同时展示数量和比例，避免只用百分比造成误读。
