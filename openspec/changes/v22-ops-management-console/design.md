## Context

系统运维管理端在 v2.2 中承接原开发人员模块和账号治理相关能力。它的职责是保证智能工单处理链路稳定、可观测、可调试，而不是直接处理员工工单。旧 `add-developer-workbench` 提案仍保留开发人员模块和用户配额口径，本提案改为账号、流程、策略、健康四类治理能力。

## Goals / Non-Goals

**Goals:**

- 提供账号管理，维护员工、服务台处理人员和系统运维人员的角色状态。
- 提供流程监控，展示状态机画布、Trace 决策树和节点输入输出。
- 提供策略调试，覆盖 Prompt 版本、RAG 检索调试和 Agent 调用统计。
- 提供系统健康，覆盖 Token 用量、服务依赖健康和异常日志定位。

**Non-Goals:**

- 不做 per-user 计费、配额售卖或自动拒绝员工请求。
- 不实现企业级 SSO、多租户组织架构和细粒度权限矩阵。
- 不在本端处理普通业务工单或替代服务台审核工作台。

## Decisions

1. **运维端统一使用 `/api/admin/*` 管理接口。**  
   现有鉴权先保持 admin 级别，后续可扩展 developer/ops 角色。

2. **流程监控以工单为主索引。**  
   状态机画布展示全局节点模型，Trace 决策树展示单工单实际执行路径，两者互补。

3. **策略调试不直接修改业务数据。**  
   RAG 调试只透传查询，Prompt 版本通过显式激活生效，Agent 统计只读聚合。

4. **Token 成本保持系统级统计。**  
   保留 model、call_type、日期维度，不做用户账单和 per-user 配额，符合内部服务台场景。

## Risks / Trade-offs

- **运维功能和服务台管理混淆** -> 文档和导航明确：账号、流程、策略、健康属于系统运维管理端；受理、审核、知识维护属于服务台处理端。
- **Trace 数据缺失导致画布空洞** -> 状态机画布可基于静态节点渲染，Trace 决策树根据实际 span 渲染，缺字段时展示待补齐提示。
- **Prompt 激活误操作影响处理质量** -> 激活、回滚必须记录操作日志，支持回滚到上一版本。
