## ADDED Requirements

### Requirement: 业务架构必须以工单生命周期为主线

系统架构说明 SHALL 以工单生命周期组织业务，而不是以 RAG、Trace、多 Agent 等技术组件作为主线。

工单生命周期 MUST 至少覆盖以下阶段：

- 服务请求发起
- 自助预诊断
- 材料采集
- 智能提单
- 分类、优先级与风险识别
- 知识增强处理
- 质量审核
- 人工接管
- 用户补充
- 结果验收
- 申诉升级
- 归档复盘

#### Scenario: 评审查看架构图

- **WHEN** 评审查看功能架构图
- **THEN** 架构图 MUST 能看出系统围绕工单提交、处理、审核、反馈和复盘展开
- **AND** 不得只呈现 RAG、Trace、Agent、接口、入库等技术名词清单

#### Scenario: 解释一个模块的业务价值

- **WHEN** 需要解释任一功能模块
- **THEN** 说明 MUST 包含该模块处理的工单生命周期阶段
- **AND** 说明 MUST 包含该模块服务的角色或业务对象

### Requirement: 角色职责必须映射到工单处理流程

系统 SHALL 将登录角色和非登录处理引擎映射到工单处理流程中的职责。

角色定义 MUST 至少包含：

- 工单提交人
- 工单审核员
- 系统管理员
- 开发运维人员
- 智能处理引擎

#### Scenario: 解释用户模块

- **WHEN** 解释用户侧功能
- **THEN** 系统 MUST 将其描述为服务请求门户
- **AND** 覆盖服务档案、预诊断、智能提单、材料采集、进度协同、补充沟通、结果验收、申诉复盘

#### Scenario: 解释管理员模块

- **WHEN** 解释管理员侧功能
- **THEN** 系统 MUST 说明管理员参与工单受理、人工审核、知识维护、账号管理、运营分析和操作审计
- **AND** 账号管理 MUST 归属于系统管理员职责，而不是普通用户职责

#### Scenario: 解释开发人员模块

- **WHEN** 解释开发人员模块
- **THEN** 系统 MUST 说明开发运维人员不直接处理普通业务工单
- **AND** 系统 MUST 说明该角色用于诊断分类错误、检索未命中、回答质量差、流程卡住、成本异常和服务健康问题

### Requirement: 智能技术必须说明输入输出和业务价值

系统 SHALL 将智能技术表述为业务流程中的处理方法，并说明输入、输出、算法方法和业务价值。

关键智能方法 MUST 至少包含：

- 工单意图抽取
- 分类与风险识别
- 混合检索融合
- 交叉编码重排
- 知识增强生成
- 质量审核评分
- 升级与恢复编排

#### Scenario: 解释 RAG 能力

- **WHEN** 解释 RAG 相关能力
- **THEN** 系统 MUST 将文档解析、分块、入库描述为知识维护支撑过程
- **AND** 系统 MUST 将真正服务工单处理的智能方法描述为混合检索、融合排序、重排和知识增强生成

#### Scenario: 解释智能算法模块

- **WHEN** 解释智能算法模块
- **THEN** 系统 MUST 避免只写 RAG 接口、文档解析分块、知识库入库、Trace 或多 Agent 协作闭环
- **AND** 系统 MUST 说明每个智能方法的输入、输出、处理算法和业务价值

### Requirement: 任务拆分必须从业务流程推导功能模块

系统后续任务拆分 SHALL 先基于工单业务流程和角色职责推导功能模块，再拆分代码、页面、接口和测试任务。

任务拆分 MUST 至少覆盖：

- 业务架构整理
- 角色职责整理
- 用户侧功能补强
- 管理员侧功能补强
- 智能处理能力凝练
- 开发运维模块解释
- 架构图与文档同步
- 验收与演示

#### Scenario: 生成后续开发任务

- **WHEN** 基于架构图生成开发任务
- **THEN** 每个任务 MUST 说明对应的业务流程阶段
- **AND** 每个任务 MUST 说明验收产物

#### Scenario: 检查任务是否偏技术堆叠

- **WHEN** 一个任务只描述接口、入库、Trace、Prompt 或 Agent 调用
- **THEN** 任务说明 MUST 补充其对应的工单业务问题、输入、输出和验收标准
