## 1. 用户角色

| 角色 | 说明 | 所属架构分区 |
| --- | --- | --- |
| 企业内部员工 / 工单提交人 | 建立员工档案，提交服务请求，补充材料，跟踪进度，验收结果，申诉升级，复盘历史工单 | 员工服务端 |
| 服务台处理人员 / 工单审核员 | 在审核工作台处理待审核工单，核查 AI 建议，提交人工决策，分析处理状态和员工反馈 | 服务台处理端 |
| 知识维护员 | 上传处理手册、FAQ、故障经验和业务规则，审核知识入库与发布，更新知识内容 | 服务台处理端 |
| 系统管理员 / 开发运维人员 | 管理账号角色，监控流程状态，调试 Agent / RAG / Prompt，监控 Token 成本、Agent 调用统计与服务健康 | 系统运维管理端 |
| 智能处理引擎 | 非登录角色，执行工单理解分类、知识检索增强、智能体协同和流程编排 | 智能算法与关键技术 |

当前系统已实现轻量登录鉴权：内部员工、服务台处理人员和系统运维人员通过 `/api/auth/login` 登录，业务 API 由 session 保护；`auth_enabled=false` 时可在演示环境放行。审核员与开发运维人员在毕设阶段仍通过 `reviewer_id` / `admin` 标识区分，不实现企业级角色权限、审核员认领、多人会签、SSO 等。

### 2.1 员工服务端（U-01 ~ U-08，8 个）

员工服务端最终定位为**企业内部员工的服务请求门户**，不是单一“提单入口”。它覆盖员工从发现问题、整理材料、发起服务请求、跟踪处理、补充信息、验收结果到申诉复盘的完整业务链条。账号、会话、联系方式和部门岗位作为员工档案能力收敛到 U-01，不再单独占用多个业务模块标题。

#### U-01 服务账号与档案

员工通过账号密码进入系统，系统通过 session cookie 维持登录态，并提供当前会话查询与退出能力。员工可维护昵称、联系方式、部门岗位、常见问题偏好和服务身份上下文，保证后续工单跟进、材料提示和人工复核能够关联到明确的服务对象。

验收标准：

- 支持用户名 + 密码登录，登录成功写入 session cookie。
- 未登录访问业务 API 时返回 401。
- 支持查询当前登录状态（`GET /api/auth/me`）。
- 支持退出登录（`POST /api/auth/logout`），session 失效。
- 设置页和 API 不暴露真实密钥内容。
- 支持自助注册服务身份，用户名唯一，密码长度 ≥ 8 字符。
- 注册成功后建立基础用户档案，`vip_level=0`、`status=active`、`preferred_categories=[]`。
- `GET /api/users/me` 返回当前用户资料（`nickname` / `contact` / `preferred_categories` / `vip_level` / `created_at`）。
- `PATCH /api/users/me` 可修改 `nickname` / `contact` / `preferred_categories`。
- `preferred_categories` 必须是分类枚举（`technical` / `billing` / `complaint` / `inquiry`）子集。
- 支持修改密码，修改成功后当前 session 失效，强制重新登录。

#### U-02 自助预诊断

员工正式提交工单前，系统根据问题描述、偏好分类和历史工单，提示可能的问题类型、紧急程度、风险等级和所需材料。该能力用于降低员工不知道如何报障的问题，避免所有工单都只表现为“提交一段文本”。

验收标准：

- 前端提单页支持在员工输入描述后展示预诊断摘要。
- 预诊断内容包括建议分类、建议优先级、是否可能需要人工审核、材料清单提示。
- 预诊断不直接创建工单，员工确认后才进入 U-03 智能提单。
- 预诊断失败时不阻塞提单，前端展示“可直接提交，系统将在后台继续识别”。
- 预诊断结果只作为辅助提示，最终分类和优先级以后端工作流结果为准。

#### U-03 智能提单

员工不需要填写传统复杂表单，只需用自然语言描述问题。后端 `TicketIntentAgent` 自动结构化标题、分类、优先级、影响范围和联系方式，并创建正式工单。

验收标准：

- 内容为空时应拒绝或提示。
- 后端先调用 `TicketIntentAgent` 提取标题、分类、优先级、影响范围、联系方式等字段。
- 提交成功后返回 `ticket_id`，工单初始状态为 `received`。
- 后台自动触发工作流。
- 支持批量提交（单次提交数量限制在合理范围，每条独立生成 ID，单条失败不影响其他）。

#### U-04 材料采集

不同类型工单需要的上下文不同。系统在提单和处理过程中采集订单号、支付流水、错误截图、设备环境、影响范围等材料，减少审核员和 Agent 因信息不足而反复请求补充。

验收标准：

- 提单页根据预诊断分类提示可选材料清单。
- 技术类工单提示错误截图、复现步骤、设备或环境信息。
- 账务或服务核查类工单提示订单号、支付流水、扣费时间、系统入口等。
- 投诉类工单提示诉求、影响范围和期望处理方式。
- 材料可作为工单 metadata 或补充消息保存，后续进入 Agent 处理上下文。
- 缺少关键材料时，系统可进入 `waiting_user_input` 等待员工补充。

#### U-05 进度协同

员工可持续跟踪自己提交的服务请求，包括列表筛选、详情查看、状态流转、处理时间线和实时节点进度。该能力体现员工不是“提交后等待结果”，而是参与工单处理过程。

验收标准：

- `GET /api/tickets` 支持按 `status` / `category` / `priority` 筛选，按时间倒序分页。
- `GET /api/tickets/{ticket_id}` 返回工单详情（含 trace 摘要、处理结果、补充消息）。
- 员工只能查询自己提交的工单（越权访问返回 403）。
- 详情页支持展示完整处理时间线（节点级进度）。
- 支持通过 WebSocket 接收工单状态变化和审核事件提示。

#### U-06 员工补充与双向沟通

当 Agent 或审核员判断上下文不足时，工单进入 `waiting_user_input`，员工可补充订单号、系统入口、设备环境、截图说明等关键信息，推动处理继续进行。补充信息不仅是一次提交动作，也是员工与系统、审核员之间的业务协同。

验收标准：

- 工单进入 `waiting_user_input` 状态后，详情页显示员工补充输入框。
- `POST /api/tickets/{ticket_id}/messages` 写入员工补充消息。
- 用户提交补充信息后，系统构造 `conversation_context`，从 `process` 节点恢复处理。
- 补充后的工单仍需经过 `ReviewerAgent` 质量审核，不能绕过 `review` 节点直接完成。
- 非 `waiting_user_input` 状态提交补充消息返回 409。

#### U-07 处理结果验收

工单完成后，用户查看处理方案、AI 依据摘要、人工审核结果和关键时间线，并确认问题是否解决。验收动作把“系统给出答案”转化为“用户确认服务完成”。

验收标准：

- 仅 `completed` 状态工单可进行结果验收。
- 详情页展示处理结果、处理依据摘要、人工审核记录摘要和最终状态。
- 用户可提交 `rating=satisfied` 表示问题已解决。
- 每个工单仅允许一次正式验收反馈，重复提交返回 409。
- 满意反馈进入满意度统计（详见 2.6 跨模块共享）。

#### U-08 申诉升级与历史复盘

用户对处理结果不满意时，可提交原因并发起申诉升级，系统自动进入人工复核或二次处理。用户还可以查看历史工单、反馈记录和相似问题处理经验，形成服务经验复用。

验收标准：

- `POST /api/tickets/{ticket_id}/feedback` 入参：`rating=dissatisfied` + `comment`。
- 不满意反馈自动触发 `user_request` 人工审核（详见 A-01）。
- 申诉原因写入反馈记录，审核工作台可查看。
- 历史工单列表支持按状态、分类、优先级和反馈结果筛选。
- 详情页可查看历史处理结果、补充消息和最终反馈。

### 2.2 服务台处理端与系统运维管理端（A-01 ~ A-07，7 个）

#### A-01 人工审核工作台

对 AI 处理路径无法可靠闭环的工单转入人工审核流程。详细设计见 [01_正式设计/09_人工审核工作台设计.md](../01_正式设计/09_人工审核工作台设计.md)。

**触发场景**：

| 场景 | 触发条件 | 默认推荐决策 |
| --- | --- | --- |
| 投诉 / P0 升级 | 路由判断为 complaint 或 P0 | reprocess 或 reject |
| AI 审核失败兜底 | retry_count ≥ 3 且 review_score < 阈值 | rewrite 或 reject |
| 处理异常 | 工作流执行抛出未恢复异常 | reprocess |
| 员工主动申请 | 工单完成后员工反馈不满意（U-08） | reprocess |

**功能验收标准**：

- 工单进入 `human_review_wait` 节点时状态变为 `pending_human_review`。
- `human_reviews` 表中插入一行 pending 记录，关联 `CoordinatorAgent` 生成的辅助决策建议。
- WebSocket 广播 `review_requested` 事件。
- 审核工作台支持按 `trigger_type` / `category` / `priority` 筛选待审核队列，双栏布局（详见 [07_前端页面与交互设计.md](../01_正式设计/07_前端页面与交互设计.md) 第 2.7 节）。
- 审核员可提交 5 种决策：`approve`（通过）/ `rewrite`（改写）/ `reprocess`（重处理）/ `reject`（驳回）/ `request_info`（请求补充）。
- `decision=rewrite` 时必须填写 `rewritten_result`。
- `decision=request_info` 后工单状态变为 `waiting_user_input`，暂不恢复工作流，等待 U-06。
- 提交决策后（除 `request_info`）工作流自动恢复，按决策结果路由。
- WebSocket 广播 `review_decided` 事件。

**非功能验收标准**：

- 同一工单同时只能有一个 pending 审核记录，重复提交决策返回 409。
- 决策记录不可修改，但可触发新的 `user_request` 审核。
- 审核过程被 trace 系统完整记录，包含 `human_decision` span。

#### A-02 知识库管理

管理员可上传知识文档，供处理 Agent 检索使用。

验收标准：

- 上传时必须包含标题和正文。
- 上传成功后返回分块数量。
- 知识库不可用时接口返回明确错误。
- **v2.0**：上传链路调用 rag-service `/ingest`，由 rag-service 完成解析 → 分块 → 向量化 → 写入 Qdrant。主系统不再直接持有 Qdrant 连接（详见 I-07 工具层与第 2.5 节）。
- 支持文档 CRUD：列表、详情、删除、按标题搜索。

#### A-03 知识库版本回滚

按版本回滚到历史文档版本。

验收标准：

- 每次 ingest 写入一条 `document_version` 记录（含 `content_hash`、`chunk_count`、`operator`、`created_at`）。
- `GET /api/admin/knowledge/{doc_id}/versions` 列出文档所有版本。
- `POST /api/admin/knowledge/{doc_id}/versions/{version}/rollback` 触发 rag-service 用旧版本内容重新 ingest（写入新版本行，保留历史完整性）。
- 回滚操作记入操作日志（详见 A-07）。

#### A-04 账号管理

系统管理员可查看、封禁、解封账号，并维护企业内部员工、服务台处理人员、系统运维人员的角色与状态。Token 成本在系统运维管理端中按系统维度统计，不在账号管理中做 per-user 配额覆写。

| 子能力 | 说明 |
| --- | --- |
| 账号列表 | 分页查询、按状态 / 角色筛选、关键字搜索 |
| 角色状态维护 | 调整账号角色（user / admin / developer）与账号状态 |
| 封禁 / 解封 | 修改账号状态，封禁后无法提交工单或访问管理功能（业务 API 返回 403） |

验收标准：

- `GET /api/admin/users` 返回用户列表，含用户状态、角色、创建时间和最近工单摘要。
- `PATCH /api/admin/users/{user_id}` 可更新用户状态和角色。
- 封禁用户调用业务 API 时返回 403。
- 封禁 / 解封等写操作记入操作日志（详见 A-07）。

#### A-05 决策采纳率统计

衡量 `CoordinatorAgent` 在人工审核场景下生成的辅助决策建议被审核员采纳的比例，作为算法效果评估指标。

验收标准：

- 审核统计接口返回 `ai_adoption_rate`。
- 支持按时间区间（日 / 周 / 月）聚合。
- 支持按 `trigger_type` 分组（escalation / quality_gate / boundary / error_fallback）。
- 决策一致定义为：审核员最终决策与 `CoordinatorAgent` 推荐决策一致（rewrite 与 reprocess 视为不同决策）。

#### A-06 系统配置查看

管理员可只读查看系统当前关键配置摘要，不可修改。

验收标准：

- `GET /api/admin/config` 返回当前运行配置摘要，包括：
  - LLM 模型名（如 `gpt-4o-mini`）
  - Qdrant URL
  - rag-service URL（`RAG_SERVICE_URL`）
  - 数据库连接状态（host / port / database name，不暴露密码）
  - 各 Agent 当前激活 Prompt 版本号
  - Token 成本统计配置摘要（模型单价、统计开关，不包含用户配额）
- 任何密钥、密码、API Key 字段不展示（即使是脱敏也不展示，直接返回 `"***"` 或省略字段）。
- 不提供任何修改端点（系统配置只能通过环境变量 / 配置文件部署期修改）。
- 页面顶部明确标注「只读视图，配置修改请联系开发人员」。

#### A-07 操作日志审计

记录管理员的所有写操作，便于事后追溯。

验收标准：

- `audit_logs` 表记录字段：`admin_id` / `action` / `target_type` / `target_id` / `detail`（JSON）/ `created_at` / `ip`。
- 覆盖以下写操作：
  - 审核决策（A-01 的 5 种 decision）
  - 账号封禁 / 解封 / 角色调整（A-04）
  - 知识库删除 / 版本回滚（A-02 / A-03）
  - Prompt 版本激活 / 回滚（D-02）
- `GET /api/admin/audit-logs` 支持按 `admin_id` / `action` / `target_type` / 时间区间筛选，按时间倒序分页。
- 日志保留 90 天，超期自动归档或删除（部署期通过 cron / 定时任务执行）。
- 日志一经写入不可修改、不可删除（业务层禁止 UPDATE / DELETE 操作）。

### 2.3 系统运维管理端（D-01 ~ D-06，6 个）

详细设计见 [13_开发人员工作台设计.md](../01_正式设计/13_开发人员工作台设计.md) 与 [12_Token成本控制台设计.md](../01_正式设计/12_Token成本控制台设计.md)。

#### D-01 Trace 决策树

开发人员可按工单查看完整执行树与决策点。详细设计见 [13_开发人员工作台设计.md](../01_正式设计/13_开发人员工作台设计.md) 第 4 节。

验收标准：

- `GET /api/admin/traces/{ticket_id}` 返回工单完整 trace（span 树）。
- `GET /api/admin/traces/{ticket_id}/decisions` 返回该 trace 所有决策点结构化数据。
- 每个决策点包含五元组：`trigger` / `options` / `selection` / `execution`（`reflection` 毕设范围可省）。
- 决策点覆盖 6 类节点：classify（routing）、route（branching）、process（tool_selection）、review（quality_gate）、retry_check（boundary）、human_review_wait（escalation）。
- 修复 v1.1 的 5 个 P0 埋点问题（详见 [13_开发人员工作台设计.md](../01_正式设计/13_开发人员工作台设计.md) 第 11 节）：
  1. `traces.total_tokens` 不再恒为 0
  2. Memory 加载有独立 `memory_call` span
  3. RAG 检索写入 `rag_stats`（hit_count / top_score / mode）
  4. 条件路由（retry_check / should_review）有独立 span
  5. classify 决策保留 options / confidence / reason 全字段
- 前端支持按决策类型徽章颜色区分（routing 蓝 / branching 紫 / quality_gate 青 / boundary 橙 / escalation 红）。
- 置信度色阶：< 0.5 红 / [0.5, 0.7) 橙 / [0.7, 0.9) 黄 / ≥ 0.9 绿。

#### D-02 Prompt 版本对比

5 个 Agent（Intent / Classifier / ReActProcessor / Reviewer / Coordinator）的 Prompt 模板从源码硬编码迁移到数据库版本管理。详细设计见 [13_开发人员工作台设计.md](../01_正式设计/13_开发人员工作台设计.md) 第 5 节。

验收标准：

- `prompt_versions` 表存储版本（`agent_name` + `version` 唯一），含 `template` / `is_active` / `note`。
- 同一 `agent_name` 最多一条 `is_active=true`，激活在事务中完成。
- `GET /api/admin/prompts/{agent_name}/versions` 列出版本，激活版本带 ★ 标记。
- `POST /api/admin/prompts/{agent_name}/versions` 新建版本（可从当前激活版本复制）。
- `POST /api/admin/prompts/{agent_name}/versions/{version}/activate` 激活指定版本。
- 回滚操作不直接改历史版本，而是复制旧版本为新行（version 自增、note 标注 "rollback to vX"）后激活，保证版本链完整。
- Agent 启动时从 DB 加载激活版本模板；找不到时降级到源码默认常量（保证首次部署可运行）。
- 前端 diff 视图支持 split / unified 切换。
- 激活 / 回滚操作记入操作日志（A-07）。

#### D-03 RAG 检索调试器

开发人员可独立输入查询语句，调试 rag-service 的检索效果。详细设计见 [13_开发人员工作台设计.md](../01_正式设计/13_开发人员工作台设计.md) 第 6 节。

验收标准：

- `POST /api/admin/rag/debug` 透传到 rag-service，请求体含 `query` / `mode` / `top_k` / `rerank` / `collection`。
- 支持三种检索模式：`vector`（向量）/ `bm25`（关键词）/ `hybrid`（RRF 融合，默认）。
- 结果对比表并排展示「原始分」与「重排分」，标注排名变化（↑↓）。
- 片段详情可展开查看原文、score、metadata（doc_id / page / chunk_index / source）。
- 主系统不在本地做任何检索逻辑，全部由 rag-service 承担。
- rag-service 不可达时返回 503，前端展示明确降级提示。

#### D-04 Token 成本控制台

按日 / 周 / 月维度统计系统级 Token 用量与折算成本，不按用户分摊，不做 per-user 配额管理。详细设计见 [12_Token成本控制台设计.md](../01_正式设计/12_Token成本控制台设计.md)。

| 子能力 | 说明 |
| --- | --- |
| 用量汇总 | `GET /api/admin/stats/tokens` 按日返回 model × call_type 分组用量 |
| 日明细 | `GET /api/admin/stats/tokens/daily` 指定日期明细 |
| 小时热力图 | `GET /api/admin/stats/tokens/hourly` 按小时聚合 LLM 调用 |

验收标准：

- `call_type` 枚举覆盖 6 个值：`intent` / `classify` / `process` / `review` / `coordinator` / `rag`。
- `traces.total_tokens` 在每个 LLM span 收尾时累加（修复 v1.1 P0 bug）。
- `token_daily_stats` 表通过 MySQL UPSERT 实现累加（`ON DUPLICATE KEY UPDATE`）。
- 统计维度仅保留日期、模型、调用类型、工单和系统总量，不暴露用户计费口径。
- 前端复用 explore/farm-manager 的 TokenDashboard 架构，移除用户筛选和配额卡。

#### D-05 Agent 调用统计

5 个 Agent 的调用次数、平均耗时、成功率、错误率统计，支持时间范围筛选。

验收标准：

- `GET /api/admin/stats/agents` 返回 5 Agent（`ticket_intent` / `classifier` / `react_processor` / `reviewer` / `coordinator`）的聚合指标：
  - `call_count`：调用次数
  - `avg_duration_ms`：平均耗时
  - `p95_duration_ms`：95 分位耗时
  - `success_rate`：成功率（success / total）
  - `error_rate`：错误率（failed / total）
- 支持查询参数：`start_date` / `end_date` / `agent_name`（可选筛选单个 Agent）。
- 数据源：基于 trace span 表聚合，按 `span.type='llm_call'` + `span.name` 分组。
- 错误率 = 失败 span 数 / 总 span 数；失败定义为 `span.status='ERROR'`。
- 支持按 `call_type` 二级维度下钻（如 `react_processor` → `process` / `process_retry`）。
- 前端默认按 `call_count` 倒序展示，提供柱图 + 表格两种视图。

#### D-06 服务健康检查

实时探测 rag-service、Qdrant、LLM、Embedding 等外部依赖的健康状态。

验收标准：

- `GET /api/admin/health` 返回各组件健康状态：

  ```json
  {
    "rag_service": { "status": "ok" | "degraded" | "down", "latency_ms": 35 },
    "qdrant": { "status": "ok", "latency_ms": 8 },
    "llm": { "status": "ok", "latency_ms": 320 },
    "embedding": { "status": "ok", "latency_ms": 45 }
  }
  ```

- rag-service：调用 `GET {RAG_SERVICE_URL}/health`。
- Qdrant：通过 rag-service 间接探测（不直接访问），或调用 rag-service `/health` 的 `components.qdrant`。
- LLM：发起一次极简 ping 请求（`max_tokens=1`），记录耗时与状态。
- Embedding：发起一次单句向量化请求，记录耗时与状态。
- 前端每 30 秒自动刷新一次，状态色阶：ok 绿 / degraded 黄 / down 红。
- 任一关键组件 down 时，前端顶部展示告警 banner。

### 2.4 智能算法与关键技术（I-01 ~ I-08，8 个）

详细设计见 [01_正式设计/01_多智能体协同架构.md](../01_正式设计/01_多智能体协同架构.md)。

#### I-01 TicketIntentAgent

自然语言工单结构化。

验收标准：

- 输入：用户自然语言描述。
- 输出字段：标题、分类、优先级、影响范围、联系方式。
- 支持模糊输入（缺字段时尝试从上下文推断，无法推断时填默认值并标注 `confidence`）。
- 调用一次 LLM，结果以 JSON Schema 校验，失败重试 ≤ 2 次。
- 写入 `intent_call` span，含 `extracted_fields` 与 `confidence`。

#### I-02 ClassifierAgent

分类 + 优先级 + 风险识别。

验收标准：

- 分类范围：`technical` / `billing` / `complaint` / `inquiry`。
- 优先级范围：`P0` / `P1` / `P2` / `P3`。
- 风险识别：标记是否涉及资金、用户安全、合规。
- 输出含 `options` / `confidence` / `reason`，写入 `classify` span（修复 v1.1 P0 埋点 #5）。

#### I-03 ReActProcessorAgent

ReAct 推理、工具调用、解决方案生成、RAG 调用与降级。

验收标准：

- 处理结果不能为空，写入工单详情。
- 处理失败时记录错误或进入降级逻辑。
- **v2.0**：处理过程的 RAG 上下文通过 `tools/rag_client.py` 调用 rag-service；rag-service 不可达时走「无知识增强」分支，工单仍能完成。
- RAG 调用写入 `rag_stats`（`hit_count` / `top_score` / `mode`），修复 v1.1 P0 埋点 #3。
- 工具调用次数受配置上限约束，防止 ReAct 死循环。

#### I-04 ReviewerAgent

处理结果质量评分。

验收标准：

- 评分范围 0 到 1。
- 默认通过阈值 0.7（可配置）。
- 重试次数不超过配置上限（默认 3）。
- 达到重试上限后转入人工审核（A-01），不直接把低质量结果返回给用户。

#### I-05 CoordinatorAgent

升级摘要、失败分析、报告生成、辅助决策建议。

验收标准：

- 在人工审核场景生成辅助决策建议（`recommend_decision` + `reason` + `confidence`）。
- 失败分析输出结构化报告，写入 trace。
- 建议质量用 `ai_adoption_rate`（A-05）反向评估。

#### I-06 LangGraph 编排

状态机定义、节点函数、条件路由、人工恢复子图。

验收标准：

- 工单状态机覆盖：`received` → `classifying` → `processing` → `reviewing` → `pending_human_review` → `waiting_user_input` → `completed` / `failed`。
- 条件路由（`retry_check` / `should_review`）有独立 span（修复 v1.1 P0 埋点 #4）。
- 支持人工恢复：审核员提交决策后从挂起节点恢复执行。

#### I-07 工具层（含 RAG Client）

Agent 调用的所有外部工具封装，核心是 RAG Client。

验收标准：

- `tools/rag_client.py` 通过 HTTP 调用 rag-service（`/retrieve` / `/rerank` / `/ingest` / `/health`）。
- 主系统不直接持有 Qdrant 连接，所有向量操作走 rag-service。
- rag-service 不可达时降级（`/health` 探测，degraded 时跳过 `/rerank`）。
- 工具层还包含通知工具、统计工具、DB 工具等基础能力。

#### I-08 决策追踪

trace / span 结构化、决策点五元组、token 统计累加。

验收标准：

- 所有 Agent 调用必有 span，所有条件路由必有 decision 子结构。
- 决策点五元组：`trigger` / `options` / `selection` / `execution` / `reflection`（毕设范围 `reflection` 可省）。
- `traces.total_tokens` 在每个 LLM span 收尾时累加（修复 v1.1 P0 埋点 #1）。
- Memory 加载有独立 `memory_call` span（修复 v1.1 P0 埋点 #2）。

### 2.5 rag-service 独立项目需求（支撑 I-07）

rag-service 作为独立项目，对内服务主系统工单处理，对外可独立部署复用。详细设计见 [11_RAG服务独立项目设计.md](../01_正式设计/11_RAG服务独立项目设计.md)。

#### 2.5.1 文档解析

支持 PDF / Markdown / TXT 三种格式的解析与分块。

验收标准：

- `POST /parse` 接收 `file` 或 `text`，返回 `doc_id` + `chunks[]` + `layout_summary`。
- PDF 解析支持版面分析（标题 / 段落 / 表格 / 图片 / 公式分类）、表格识别（行列结构化）、阅读顺序还原。
- 分块策略三选一：`structure_aware`（默认，按标题层级）/ `semantic`（按句子 Embedding 边界）/ `fixed`（固定窗口 + 重叠）。
- 每个 chunk 携带 metadata：`source` / `page` / `category` / `heading_path` / `doc_id` / `chunk_index`。
- 错误码：`400 UNSUPPORTED_FORMAT` / `422 PARSE_FAILED` / `507 MODEL_UNAVAILABLE`。

#### 2.5.2 文档入库

完整链路：解析 → 分块 → 向量化 → 写入 Qdrant。

验收标准：

- `POST /ingest` 接收文档与目标 collection，返回 `doc_id` / `chunk_count` / `collection`。
- 同 `doc_id` 重新 ingest 时按 `content_hash` 判断是否变化，未变化跳过，变化则删除旧 chunk 再写入。
- 每次 ingest 写入一条 `document_version` 记录，支持回滚（A-03）。
- 错误码：`404 COLLECTION_NOT_FOUND` / `422 INGEST_FAILED` / `503 QDRANT_UNAVAILABLE`。

#### 2.5.3 检索模式

| 模式 | 端点 | 实现 | 适用场景 |
| --- | --- | --- | --- |
| `vector` | `/retrieve?mode=vector` | Qdrant dense + 余弦距离 | 语义相似、查询与文档表达不一致 |
| `bm25` | `/retrieve?mode=bm25` | Qdrant sparse（内置 BM25）/ jieba 分词 | 专有名词、产品型号、错误码精确匹配 |
| `hybrid` | `/retrieve?mode=hybrid`（默认） | RRF 融合（k=60，向量 0.7 + BM25 0.3） | 通用推荐 |

验收标准：

- `POST /retrieve` 入参：`query` / `collection` / `mode` / `top_k`（默认 10）/ `filters`（元数据过滤）/ `use_hyde`（默认 false）。
- 响应 `data.results[]` 每项含 `content` / `score` / `doc_id` / `chunk_index` / `metadata`。
- HyDE 查询改写可选启用，启用时增加一次 LLM 调用，用于 query 过短或抽象场景。
- 错误码：`400 INVALID_MODE` / `503 QDRANT_UNAVAILABLE`。

#### 2.5.4 Cross-Encoder 重排

验收标准：

- `POST /rerank` 入参：`query` / `documents[]` / `top_k`（默认 5）/ `model`（默认 `BAAI/bge-reranker-v2-m3`）。
- 响应按相关性降序返回重排后的文档列表。
- 模型加载失败时降级为按原始 score 排序，响应携带 warning 标记（不返回 500）。
- 错误码：`507 RERANKER_MODEL_UNAVAILABLE`。
- 主流程典型用法：`/retrieve` 召回 top-20 → `/rerank` → 取 top-5 作为最终上下文。

#### 2.5.5 健康检查

验收标准：

- `GET /health` 返回 `{ "status": "ok" | "degraded", "components": { "qdrant", "embedder", "reranker" } }`。
- 任一关键组件不可用则 `status=degraded`。
- 主系统 `tools/rag_client.py` 定期探测 `/health`，degraded 时跳过 `/rerank`，仅用 `/retrieve`。
- D-06 服务健康检查聚合展示 rag-service 健康状态。

#### 2.5.6 集合与文档管理

验收标准：

- `POST /collections` 创建 collection（指定向量维度、距离度量）。
- `DELETE /collections/{name}` 删除 collection。
- `GET /collections/{name}/documents` 分页查询文档元数据（`doc_id` / `chunk_count` / `metadata` / `ingested_at`）。
- 元数据存于 rag-service 自带 SQLite（`storage/metadata_store.py`），不污染主系统 MySQL。

### 2.6 跨模块共享功能

跨业务模块复用的基础能力，不单独编号但属于系统必需。

| 功能 | 说明 | 对应编号 |
| --- | --- | --- |
| 实时进度推送 | WebSocket 订阅工单 / 全局进度，每个节点完成后推送 | 支撑 U-05 / A-01 |
| 执行追踪查询 | 按工单查询 trace / span 树（含决策点） | 支撑 D-01 / I-08 |
| 统计分析 | 分类分布、优先级分布、完成率、失败率、满意度、Token 用量 | 支撑 A-05 / D-04 / D-05 |
| 登录鉴权 | 见 U-01 服务账号与档案 | U-01 |

## 3. 非功能验收（汇总）

各功能模块的非功能验收标准分散在以上各章节，本节仅补充跨模块的统一要求。

- **可用性**：rag-service 不可达时，主系统工单主流程仍能完成（走「无知识增强」分支）。详见 [02_非功能性需求.md](./02_非功能性需求.md) 第 8 节。
- **Token 成本统计**：按系统维度统计模型调用用量和估算成本，不做用户计费或 per-user 配额。详见 [02_非功能性需求.md](./02_非功能性需求.md) 第 9 节。
- **可观测性**：所有 Agent 调用必有 span，所有条件路由必有 decision 子结构。详见 [02_非功能性需求.md](./02_非功能性需求.md) 第 11 节。
- **Trace 决策树**：5 个 P0 埋点必须修复，详见 [13_开发人员工作台设计.md](../01_正式设计/13_开发人员工作台设计.md) 第 11 节。
- **Token 统计准确率**：修复 v1.1 P0 bug 后，`traces.total_tokens` 与 `token_daily_stats` 累加值一致，准确率 100%。
- **Prompt 版本切换**：激活 / 回滚操作响应时间 < 500ms，agent 加载激活模板缓存生效时间 < 5 秒。
- **RAG 调试器**：单次调试请求响应时间 < 2 秒（含 retrieve + rerank），失败时返回明确错误码。
- **操作日志保留**：90 天，超期归档；日志不可修改、不可删除。
