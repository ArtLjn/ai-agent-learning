# 非功能性需求

> 版本：v2.1
> 日期：2026-07-09
> 状态：v2.1 对齐业务架构梳理；Token 章节改为系统级成本可观测，不做 per-user 配额
> 关联变更：[README.md](../README.md) v2.1 摘要、[01_核心功能需求.md](./01_核心功能需求.md) v2.1 功能清单

## 1. 可用性

系统应支持本地开发环境稳定运行。即使 LLM 或 Qdrant 暂时不可用，核心工单流程也应通过降级逻辑继续运行。

要求：

- 后端启动失败时应输出明确日志。
- Qdrant 初始化失败不影响 API 主服务启动。
- Agent 调用失败时应进入重试或降级逻辑。
- **v2.0**：rag-service 启动失败不影响主系统启动；主系统 `tools/rag_client.py` 探测到 rag-service 不可达时走「无知识增强」分支。

## 2. 响应性能

系统面向演示和本科毕设，不要求高并发生产性能，但应满足基本交互体验。

要求：

- 工单提交接口应快速返回，不等待完整工作流结束。
- 后台处理过程通过 WebSocket 更新。
- 列表查询、详情查询和审核队列查询应在演示环境中快速响应。
- **v2.0**：rag-service HTTP 请求超时 10 秒，超时后重试 1 次（间隔 500ms），重试失败走降级。
- **v2.0**：开发人员工作台 Token 控制台、Trace 决策树查询响应时间 < 1 秒（毕设 demo 数据规模）。

## 3. 可维护性

代码结构应保持清晰，便于论文说明和后续修改。

要求：

- API、Agent、Workflow、Tool、Core 分层清晰。
- 新增功能优先放入已有模块边界内。
- 避免在单个文件中堆积过多职责。
- 文档与代码关键流程保持同步。
- **v2.0**：双项目边界清晰——主系统专注业务编排，rag-service 专注知识检索算法；两者通过 HTTP API 解耦，可独立演进。

## 4. 可测试性

系统应具备自动化测试基础。

要求：

- 覆盖工作流状态流转。
- 覆盖核心 Agent 降级逻辑。
- 覆盖主要 API 接口。
- 测试不依赖真实外部 LLM 服务。
- **v2.0**：覆盖 rag-service 三种检索模式与降级链路。
- **v2.1**：覆盖 Token 用量聚合、成本估算和统计接口。

## 5. 可解释性

多 Agent 系统需要能解释"为什么得出这个处理结果"。

要求：

- 工单详情应展示分类、优先级、处理结果和审核评分。
- trace 接口应展示节点执行顺序和耗时。
- trace 决策接口应展示关键路由、质量门禁和重试边界判断。
- WebSocket 消息应包含当前节点和状态。
- **v2.0**：所有决策点必须有结构化五元组（trigger / options / selection / execution / reflection），详见 [13_开发人员工作台设计.md](../01_正式设计/13_开发人员工作台设计.md) 第 4 节。

## 6. 安全性

本科毕设阶段实现基础安全约束，不扩展企业级权限系统。

要求：

- 业务 API 默认要求登录。
- 密码使用哈希保存和校验，不在文档或仓库保存明文密码。
- 不提交 `.env`、密钥、凭证等敏感信息。
- API 不在日志中打印完整密钥。
- 上传知识库内容仅作为演示，不处理敏感真实数据。
- 前端设置页不应暴露真实生产凭证。
- **v2.0**：开发人员工作台 `/api/admin/*` 接口需要 admin 鉴权（与人工审核工作台同套鉴权）。

## 7. 部署性

系统应支持本地运行和 Docker Compose 演示。

要求：

- 后端可通过 `uvicorn` 启动。
- 前端可通过 `npm run dev` 启动。
- Qdrant 等依赖可通过 Docker Compose 启动。
- MySQL 连接通过 `config.yaml` 或环境变量配置，测试库和生产库应隔离。
- README 或文档中说明启动方式。

## 8. RAG 服务可用性与降级（v2.0 新增）

rag-service 作为独立项目部署，主系统通过 HTTP 调用，必须设计独立的可用性目标与降级链路。

### 8.1 可用性目标

| 指标 | 目标值 | 说明 |
| --- | --- | --- |
| rag-service 可用性 | 99% | 毕设环境单实例，不追求多副本高可用 |
| rag-service 启动时间 | < 30 秒 | 含 Cross-Encoder 模型加载 |
| `/retrieve` P95 响应时间 | < 500ms | 不含 HyDE，含 Qdrant 查询 |
| `/rerank` P95 响应时间 | < 1 秒 | top-20 重排，CPU 推理 |

### 8.2 主系统降级链路

rag-service 不可达时，主系统主流程仍能完成工单处理。

| 触发条件 | 主系统行为 |
| --- | --- |
| rag-service HTTP 请求 10 秒超时 | 重试 1 次（间隔 500ms） |
| 重试仍失败 | `rag_client.py` 抛 `RagServiceUnavailable`，ReActProcessorAgent 走「无知识增强」分支 |
| `/health` 返回 `degraded` | Agent 跳过 `/rerank`，仅用 `/retrieve` 结果 |
| rag-service 连续 3 次失败 | 标记为不可用，后续 5 分钟不再调用，直接走无 RAG 分支 |
| rag-service 内部 Cross-Encoder 加载失败 | rag-service 自身降级为按原始 score 排序，主系统不感知 |

降级原则：宁可返回次优结果（带 warning），也不直接 500，保证主系统能继续工作。

### 8.3 超时与重试约定

| 维度 | 默认值 | 可配置项 |
| --- | --- | --- |
| HTTP 超时 | 10 秒 | `config.yaml` 的 `rag_service.timeout_seconds` |
| 重试次数 | 1 次 | `rag_service.retry_count` |
| 重试间隔 | 500ms | `rag_service.retry_interval_ms` |
| 熔断窗口 | 5 分钟 | `rag_service.circuit_break_window_sec` |
| 熔断阈值 | 连续 3 次失败 | `rag_service.circuit_break_threshold` |

## 9. Token 成本可观测（v2.1 修订）

Token 控制台用于展示系统级 LLM 用量和成本估算，为论文提供真实成本数据。系统定位为服务性工单系统，用户免费提交工单，平台统一承担模型成本，因此当前版本不做 per-user 配额、用户计费或按用户分摊。详细设计见 [12_Token成本控制台设计.md](../01_正式设计/12_Token成本控制台设计.md)。

### 9.1 统计维度

| 维度 | 说明 |
| --- | --- |
| 日期 | 按日 / 周 / 月聚合，支持指定日期明细 |
| 模型 | 按模型名统计用量和估算成本 |
| 调用类型 | 按 `intent` / `classify` / `process` / `review` / `coordinator` / `rag` 分组 |
| 工单 | 可从 trace 回溯单个工单的 token 消耗 |

### 9.2 数据准确性要求

- 每个 LLM span 收尾时必须把 usage 写入 span metadata。
- `traces.total_tokens` 必须等于该 trace 下所有 LLM span 的 token 总和。
- `token_daily_stats` 通过 MySQL UPSERT 按日期、模型、调用类型累加。
- Token 控制台查询不得依赖前端临时计算，必须以服务端聚合结果为准。

### 9.3 范围边界

| 不做项 | 原因 |
| --- | --- |
| per-user 配额覆写 | 服务性工单系统不按用户分摊成本 |
| 超限自动拒绝用户请求 | 容易影响演示主流程，当前通过运维监控成本 |
| 付费套餐和计费账单 | 超出本科毕设范围 |
| 真实费用扣款 | 涉及支付系统和外部依赖 |

成本失控的防护以部署期配置、模型选择、日志告警和人工运维为主，不作为业务功能暴露给用户。

## 10. 双项目部署（v2.0 新增）

主系统与 rag-service 独立部署，通过 docker-compose 一键编排。

### 10.1 端口与进程

| 项目 | 端口 | 进程 | 启动方式 |
| --- | --- | --- | --- |
| ai-agent-learning（主系统） | 8000 | uvicorn | `uvicorn multi_agent_system.main:app --port 8000` |
| rag-service | 8001 | uvicorn | `uvicorn app.main:app --port 8001` |
| MySQL（共享） | 3306 | mysqld | docker-compose 启动 |
| Qdrant（rag-service 独占） | 6333 | qdrant | docker-compose 启动 |

### 10.2 数据库隔离

| 资源 | 归属 | 说明 |
| --- | --- | --- |
| MySQL `ai_agent_learning` 库 | 主系统 | `users` / `tickets` / `traces` / `spans` / `token_daily_stats` / `prompt_versions` / `human_reviews` / `ticket_messages` 等 |
| MySQL（不共享） | rag-service 不连接 | rag-service 不持有业务数据 |
| Qdrant collection | rag-service 独占 | 主系统不直连 Qdrant，仅通过 HTTP 调用 |
| SQLite | rag-service 私有 | 存 RAG 内部元数据（`storage/metadata_store.py`），避免污染主系统 MySQL |

### 10.3 docker-compose 一键编排

毕设演示环境通过根目录 `docker-compose.yml` 编排主系统 + rag-service + MySQL + Qdrant：

```yaml
# 仓库根 docker-compose.yml（示意）
services:
  ai-agent-learning:
    build: ./ai-agent-learning
    ports: ["8000:8000"]
    depends_on: [mysql]

  rag-service:
    build: ./rag-service
    ports: ["8001:8001"]
    depends_on: [qdrant]

  mysql:
    image: mysql:8.0
    ports: ["3306:3306"]
    volumes: ["mysql_data:/var/lib/mysql"]

  qdrant:
    image: qdrant/qdrant:latest
    ports: ["6333:6333"]
    volumes: ["qdrant_data:/qdrant/storage"]

volumes:
  mysql_data:
  qdrant_data:
```

实际部署可采用腾讯云生产服务器（43.155.217.74）共用 MySQL 实例，Qdrant 独立部署。

## 11. 可观测性（v2.0 新增）

回答答辩反馈"trace 没用、决策语义缺失"的痛点。

### 11.1 Trace 覆盖率

| 指标 | 目标 | 验证方式 |
| --- | --- | --- |
| Agent 调用 span 覆盖率 | 100% | 所有 5 个 Agent 的每次 LLM 调用必有对应 `llm_call` span |
| 工具调用 span 覆盖率 | 100% | RAG / Memory / 通知工具调用必有独立 `tool_call` span |
| 条件路由 span 覆盖率 | 100% | `route` / `retry_check` / `should_review` 必须有独立 span，不能被 LangGraph 条件边函数吞掉 |
| 人工决策 span 覆盖率 | 100% | `human_review_wait` 决策必有 `human_decision` span |

### 11.2 Token 统计准确率

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| `traces.total_tokens` 准确率 | 100% | 修复 v1.1 P0 bug 后，每个 LLM span 收尾必须累加 delta |
| `token_daily_stats` 累加一致性 | 100% | 与 `traces.total_tokens` 按日聚合结果一致 |
| `call_type` 标注完整率 | 100% | 每个 LLM span 必须显式写入 `call_type`，否则按默认 `process` 归类会污染统计 |

### 11.3 决策点结构化

所有条件路由必须有 `spans.metadata.decision` 子结构，遵循五元组：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `decision_type` | 是 | routing / branching / tool_selection / quality_gate / boundary / escalation |
| `trigger` | 是 | 触发决策的输入信号 |
| `options` | 是 | 候选方案列表 |
| `selection` | 是 | 最终选择 + 置信度 + 原因 |
| `execution` | 是 | 指向后续 span 或 downstream_node |
| `reflection` | 否 | 事后评估（毕设范围可省，预留字段） |

### 11.4 P0 埋点修复清单

v1.1 遗留的 5 个 P0 埋点问题必须在 v2.0 修复，详见 [13_开发人员工作台设计.md](../01_正式设计/13_开发人员工作台设计.md) 第 11 节：

1. `traces.total_tokens` 永远为 0
2. Memory 加载未埋点
3. RAG 检索被通用 tool_call 吞掉
4. 条件路由决策点不入 trace
5. classify 决策丢字段
