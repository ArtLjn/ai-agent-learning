# 技术选型与可行性

> **v2.0 修订（2026-07-01）**：技术栈扩展为双项目架构。新增 rag-service 独立项目的技术选型见下文「v2.0 新增」小节。

## 1. 技术栈总览

| 类别 | 技术 | 选择原因 |
| --- | --- | --- |
| 后端框架 | FastAPI | 支持异步接口、参数校验和自动生成 API 文档 |
| 工作流编排 | LangGraph | 适合表达多 Agent 状态机和条件路由 |
| 大模型接口 | OpenAI SDK 兼容接口 | 便于接入 Ollama、DeepSeek 或其他兼容服务 |
| 数据模型 | Pydantic | 与 FastAPI 结合紧密，适合请求和响应校验 |
| ORM 与数据库 | SQLAlchemy 2.0 async + MySQL | 统一异步数据访问，兼容测试环境，支撑生产式关系数据建模 |
| 向量数据库 | Qdrant | 支持语义检索，可用于 RAG 演示 |
| 前端框架 | React + TypeScript | 适合构建管理端界面，类型约束清晰 |
| UI 样式 | TailwindCSS + shadcn/ui | 快速构建一致的后台管理界面 |
| 测试框架 | pytest | Python 项目常用测试框架 |
| 容器化 | Docker Compose | 方便启动 API、前端、Qdrant 等服务 |
| 鉴权 | Starlette Session + bcrypt | 实现轻量登录保护，满足后台演示基本安全要求 |

## 2. FastAPI 可行性

FastAPI 能够满足系统接口层需求：

- 支持异步接口，适合后台执行工单工作流。
- 支持 Pydantic 模型校验，减少手写参数检查。
- 支持 WebSocket，可实现工单状态实时推送。
- 自动生成 Swagger 文档，便于联调和论文截图展示。

当前项目已经在 `src/multi_agent_system/api/app.py` 和 `src/multi_agent_system/api/routes.py` 中完成基础实现。

## 3. LangGraph 可行性

工单处理流程天然具有状态机特征：不同分类和优先级会进入不同路径，审核失败后可能重试，失败后进入兜底处理。LangGraph 适合表达这种有向图流程。

相比在普通函数里堆叠 `if/else`，LangGraph 的优势是：

- 流程节点清晰，便于画图和解释。
- 条件路由可独立维护。
- 后续扩展新节点较方便。
- 适合体现多 Agent 协同思想。

## 4. MySQL 与 SQLAlchemy 可行性

最新系统代码已经将主数据存储从早期 SQLite 方案升级为 SQLAlchemy 2.0 async + MySQL。该方案既保留异步接口能力，也更接近真实后台系统的数据管理方式。

- 使用 `create_async_engine` 和 `async_sessionmaker` 管理连接与会话。
- ORM 表集中定义在 `models/db.py`，便于论文展示实体关系。
- 业务读写统一收敛到 `DatabaseManager`，外部调用方不直接感知数据库方言。
- 兼容旧的原始 SQL 调用方式，保留 `?` 占位符适配层，降低迁移风险。
- 生产环境使用 MySQL，测试环境可以通过配置切换到独立测试库。

这次升级后，数据库不再只是本地演示文件，而是支持工单、用户、检查点、执行追踪、人工审核和统计分析的核心基础设施。

## 5. Qdrant 可行性

知识库检索是本项目的重要亮点，但不是所有演示流程都依赖知识库。Qdrant 作为可选组件使用：

- 可上传工单处理知识文档。
- 可将文档分块后写入向量库。
- 处理 Agent 在生成方案前检索相关知识片段。
- 当 Qdrant 不可用时，系统核心工单流程仍可运行。

这种设计既能展示 RAG 能力，也避免系统对外部服务过度依赖。

## 6. 前端技术可行性

React + TypeScript 适合实现本项目的后台管理端：

- 工单列表、详情、统计和设置页面都是典型管理端页面。
- TypeScript 类型定义可与后端响应结构保持一致。
- WebSocket hook 可用于实时刷新状态。
- shadcn/ui 组件能减少基础 UI 开发成本。

当前前端页面包括 `Dashboard`、`Tickets`、`TicketDetail`、`Knowledge`、`AgentMonitor` 和 `Settings`，已经覆盖毕业设计演示所需界面。

## 7. 风险与应对

| 风险 | 影响 | 应对策略 |
| --- | --- | --- |
| LLM 服务不可用 | Agent 无法生成高质量结果 | 保留关键词分类、意图提取规则、占位处理和降级逻辑 |
| Qdrant 未启动 | RAG 检索不可用 | 将知识库设为可选，核心流程继续运行 |
| 工作流异步执行难调试 | 前端状态不一致 | 使用 WebSocket 和 trace/span 记录执行过程 |
| 数据库连接失败 | API 启动或业务写入失败 | 通过配置集中管理连接串，测试环境独立建库，启动日志明确暴露失败原因 |
| 文档范围过大 | 毕设难以收尾 | 明确排除企业级权限、SLA、多人审核协作等复杂能力 |
| 测试环境差异 | 演示不稳定 | 保留 pytest 自动化测试和本地 Docker 启动方式 |

## 8. v2.0 新增技术栈（rag-service）

v2.0 起本项目拆分出独立的 rag-service（端口 8001），主系统通过 HTTP 调用其检索能力。rag-service 在主系统技术栈基础上新增以下选型：

| 技术 | 用途 | 选型理由 |
| --- | --- | --- |
| FastAPI | rag-service Web 框架 | 与主系统对齐，OpenAPI 文档自动生成 |
| Qdrant | 向量检索（独立实例） | 主系统不直接访问，由 rag-service 封装 |
| BAAI/bge-reranker-v2-m3 | Cross-Encoder 重排 | 中文场景效果好，模型大小适中 |
| rank_bm25 | BM25 关键词检索 | Python 纯实现，无需额外服务 |
| RRF（Reciprocal Rank Fusion） | 混合检索融合 | 工业标准，参数少 |
| MinerU / LayoutLMv3 | PDF 复杂解析 | 从 NSQA 项目迁移 |
| Pydantic v2 | 数据校验 | 与主系统对齐 |
| httpx | HTTP 客户端 | 支持 async，与主系统 async 体系一致 |
