## 1. 文档定位

本目录沉淀「基于多智能体协同的智能工单处理系统设计与实现」毕业设计的完整设计文档。

v2.2 起，文档对外优先使用**企业内部服务台工单业务闭环视角**描述系统：

**工单提交 -> 意图理解 -> 分类路由 -> 知识增强处理 -> 质量审核 -> 人工复核 -> 用户补充 -> 反馈归档。**

系统的核心业务定位是：**基于知识增强智能体协同的工单处理系统**。它面向企业内部服务台工单场景，工单提交人为企业内部员工，业务范围覆盖账号权限、业务系统、办公设备、网络环境、行政服务等内部服务请求。系统解决自然语言提单不规范、人工初筛成本高、常见问题重复处理、AI 输出质量不可控、高风险工单需要人工接管、处理过程难解释等问题。完整业务架构见 [04_业务架构梳理.md](./00_预设计/04_业务架构梳理.md)，定稿口径见 [2026-07-10 定稿设计](../specs/2026-07-10-ticket-processing-system-final-design.md)。

v2.0 起，项目从单一演示系统演进为**双项目协同架构**：

- **ai-agent-learning（主系统）**：FastAPI + LangGraph 工单处理 + 4 大角色模块的前端
- **rag-service（独立项目，待建）**：FastAPI + Qdrant 的可复用 RAG 服务，对内供主系统调用，对外可独立部署给其他项目复用

主系统内部按当前框架图统一为 **4 个架构分区共 29 个功能**（回应“业务要清楚、模块要看出体量”的反馈）。论文和答辩展示时先说明分区面向的用户角色，再说明每个分区支撑的工单业务：

| 架构分区 | 面向角色 | 业务职责 |
| --- | --- | --- |
| 员工服务端 | 企业内部员工 / 工单提交人 | 员工档案、工单提报、进度协同、验收反馈 |
| 服务台处理端 | 服务台处理人员 / 工单审核员 / 知识维护员 | 工单受理、人工审核、知识维护、运营分析 |
| 系统运维管理端 | 系统管理员 / 开发运维人员 | 账号管理、流程监控、策略调试、系统健康 |
| 智能算法与关键技术 | 智能处理引擎（非登录角色） | 工单理解分类、知识检索增强、智能体协同、流程编排 |

完整功能编号清单（U-/A-/D-/I- 前缀）见 [assets/system-module-architecture-v2-ascii.md](./assets/system-module-architecture-v2-ascii.md)。

## 5. 毕设范围声明（v2.0 修订）

本项目定位为本科毕业设计。v2.2 起，系统表达先绑定企业内部服务台工单业务闭环，再说明 v2.0 的系统性架构扩展：回应答辩反馈"工作量不够，要么堆算法要么堆业务"，但不把系统扩大为完整 ITSM / OA / 财务平台。

**v2.0 新增范围：**

- **rag-service 独立项目**：把 RAG 能力抽成独立服务，复用 NSQA 项目的 PDF 复杂文档处理架构，对外可复用。论文可独立成章。
- **业务化模块表达**：对外按员工服务端、服务台处理端、系统运维管理端、智能算法与关键技术四个架构分区组织。
- **4 大架构分区**：主系统按企业内部员工、服务台处理人员、系统运维管理人员和智能处理引擎的协作关系展开，回应"模块要按角色分层"。
- **开发人员工作台**：Trace 决策树、Prompt 版本对比、RAG 检索调试器、Token 成本控制台（系统级统计，复用 farm-manager 项目资产）。

**v2.0 仍坚持的克制：**

- 不做多租户 / 真实支付 / 短信邮件 / SLA 排班 / 自训练模型。
- 不引入知识图谱（KG）—— 已与导师澄清"NSQA 是独立项目，本系统未用 KG"，KG 暂搁置。
- 数据库不做读写分离 / 分库分表 / 备份恢复等生产级治理。

详细边界见 [06_项目管理/02_毕设范围控制.md](./06_项目管理/02_毕设范围控制.md)。
