# 开发计划与里程碑

## 1. 阶段划分（v2.0 修订）

v2.0 重构期总计 8-11 天，分 6 个阶段：

| 阶段 | 时间 | 主要任务 | 产出 |
| --- | --- | --- | --- |
| 阶段 0：v1.3 基线确认 | 第 1 天（已基本完成） | 确认 v1.3 现有功能稳定；归档 v1.x 文档；拉 explore/ 复用资产 | v1.3 代码冻结 + explore 资产清单 |
| **阶段 1：rag-service 项目搭建** | 第 2-3 天（2 天） | 创建 `rag-service` 独立项目；FastAPI 脚手架；Qdrant 接入；从 NSQA 迁移 PDF 复杂解析；实现 `/parse` `/ingest` | rag-service 可独立启动 |
| **阶段 2：rag-service 检索与重排** | 第 4-5 天（2 天） | 实现 `/retrieve`（向量 + BM25 + 混合）；接入 Cross-Encoder 重排 `/rerank`；`/health` | rag-service API 全通 |
| **阶段 3：主系统 RAG Client + 4 模块重构** | 第 6-7 天（2 天） | `tools/rag_client.py` + 降级策略；ReActProcessorAgent 切换调用；前端模块边界对齐 | 主系统 4 模块边界清晰 |
| **阶段 4：开发人员工作台** | 第 8-10 天（2-3 天） | Trace 决策树（复用 explore/admin_trace）；Prompt 版本对比；RAG 检索调试器；Token 控制台（复用 explore/TokenDashboard） | 开发人员模块完整可演示 |
| **阶段 5：测试与文档** | 第 11 天（1 天） | rag-service 单测 + 集成测试；主系统降级测试；docs 全量更新；论文初稿章节 | 测试报告 + 文档 v2.0 |

**总工时：8-11 天**（取决于 PDF 解析迁移的复杂度）。

## 2. 当前项目基础（v1.3 冻结）

v1.3 已具备的能力（v2.0 阶段 0 起冻结新增）：

- FastAPI 后端服务。
- LangGraph 工单工作流（receive → classify → route → process → review → notify → complete）。
- 意图理解、分类、处理、审核、协调 5 个 Agent。
- SQLAlchemy 2.0 async + MySQL 数据存储。
- Qdrant 知识库工具（v2.0 将迁移到 rag-service）。
- React 前端页面（仪表盘、工单、知识库、监控、审核工作台、设置）。
- 登录鉴权、人工审核工作台、用户补充恢复子图、执行追踪。
- 部分 pytest 测试。
- Docker 部署脚本。

v2.0 阶段 1 起的工作重点：**新增 rag-service 独立项目 + 主系统模块重构 + 开发人员工作台**。

## 3. 优先级建议

### P0：必须完成（v2.0 阶段 1-3）

- rag-service 独立项目可启动。
- rag-service 提供 `/parse` `/ingest` `/retrieve` `/rerank` `/health`。
- 主系统通过 `tools/rag_client.py` 调用 rag-service，降级策略生效。
- 主系统 4 大模块边界清晰，前端模块导航对齐。
- 数据库扩展（`prompt_versions`、`token_daily_stats`）。

### P1：建议完成（v2.0 阶段 4）

- 开发人员工作台完整功能：
  - Trace 决策树（复用 explore/admin_trace）。
  - Token 成本控制台（复用 explore/TokenDashboard）。
  - Prompt 版本对比。
  - RAG 检索调试器。

### P2：可选完成（v2.0 阶段 5）

- RAG 评估实验（Faithfulness / Answer Relevance / Context Precision）。
- rag-service 性能压测。
- 论文实验数据采集与对比表。

## 4. 关键里程碑与验收

| 里程碑 | 验收标准 |
| --- | --- |
| M1：rag-service MVP（阶段 1 结束） | rag-service 可独立启动，`/parse` 能处理 PDF/MD/文本，`/ingest` 能写入 Qdrant |
| M2：rag-service 全 API（阶段 2 结束） | `/retrieve` 支持三种模式（向量/BM25/混合），`/rerank` 接入 Cross-Encoder |
| M3：主系统切换 RAG Client（阶段 3 结束） | ReActProcessorAgent 通过 HTTP 调用 rag-service；rag-service 关闭时主流程仍能完成 |
| M4：开发人员工作台（阶段 4 结束） | 4 个子页面（Trace/Prompt/RAG调试/Token）均可演示 |
| M5：v2.0 发布（阶段 5 结束） | 测试覆盖率 ≥ 70%；docs v2.0 全量更新；论文 1-7 章初稿 |

## 5. 答辩演示脚本建议（v2.0）

1. **总体介绍**：打开论文图 1（双系统协作图），说明 v2.0 双项目架构与 4 大模块。
2. **用户模块演示**：登录系统 → 提交自然语言工单 → TicketIntentAgent 自动结构化 → 详情页查看进度。
3. **智能算法模块演示**：打开工单详情，展示 trace 决策树，每个 Agent 的 trigger/options/selection。
4. **管理员模块演示**：提交投诉工单 → 进入人工审核队列 → 审核工作台双栏布局 → 提交决策 → 工作流恢复。
5. **rag-service 独立演示**：单独启动 rag-service → 调用 `/parse` 处理 PDF → 调用 `/retrieve` 检索 → 在主系统 RAG 调试器中查看结果。
6. **开发人员工作台演示**：展示 Token 控制台日/周/月统计、Prompt 版本 diff、RAG 检索调试器三种模式对比。
7. **降级演示**：关闭 rag-service → 提交工单 → 主流程仍能完成（无知识增强分支）。
8. **展望**：说明 v3.0 计划引入 GraphRAG（借鉴 NSQA 经验）。

## 6. 风险与缓解

| 风险 | 缓解措施 |
| --- | --- |
| rag-service PDF 解析迁移复杂度超预期 | 优先迁移简单文档（MD/TXT），PDF 复杂解析作为 P1；保留个人知识库 `personal_knowledge_base` 作为降级备份 |
| 主系统调用 rag-service 网络抖动 | RAG Client 实现 10 秒超时 + 1 次重试 + 降级到无知识增强（与 02_非功能需求 / 11_RAG服务设计 保持一致） |
| Token 控制台复用 explore/ 适配成本 | 优先做 schema 适配（去 farm_id），UI 暂时保留原样；不要重写组件 |
| 双项目部署复杂度增加 | docker-compose 同时编排主系统 + rag-service；提供 `make dev` 一键启动 |
| 论文章节扩张导致超期 | 阶段 5 文档/论文撰写预留弹性时间；如阶段 1-4 超期，先砍 P2 评估实验 |
